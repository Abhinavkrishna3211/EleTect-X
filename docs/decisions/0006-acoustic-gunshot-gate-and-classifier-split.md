# ADR 0006: Acoustic pipeline — gunshot wake-gate and post-wake classifier split

- **Status:** superseded by ADR-0009 (retained as the documented fallback design if ADR 0009's LPBAM
  dual-channel concurrency test fails on the bench — see that ADR before treating anything below as the
  field plan)
- **Date:** 2026-07-28

## Context

CONTEXT.md §3 scopes INMP441 as "acoustic corroboration (>60 Hz) + anti-poaching gunshot/chainsaw," and §4 lists **gunshot trigger** as its own reflex-layer (STM32, always-on µA) duty, separate from "geophone STA/LTA + TinyML footfall." Two things needed to be worked out that CONTEXT.md leaves implicit: how INMP441 — a digital I2S MEMS mic with no analog tap — can actually be sampled on this MCU at all, and whether gunshot detection can reuse the geophone's wake-up the way footfall does, or needs its own path.

A public reference implementation for this exact chip (STM32U585, same Arduino UNO Q core) was reviewed for the capture question: `rahuljeyaraj/edgeai-predictive-monitor`, `base-station/sketch/mic_sampler.{h,cpp}`. It proves INMP441 I2S capture is achievable in App Lab's sketch environment — which has no devicetree/pinctrl hook and no `sai1_a` node in the shipped firmware — by driving SAI1_A directly through STM32 LL/CMSIS registers instead of Zephyr's unsupported i2s driver path (RCC/PLL2 domain config, GPIO AF13 on PB9/PB10/PC1, SAI1_Block_A CR1/CR2/FRCR/SLOTR by hand, GPDMA1 channel 2 / request 36 with single-block linked-list init). This resolves an earlier open question about whether SAI1 is TrustZone-locked on this board: it's locked for the *devicetree-driven* path, not for raw register access.

That implementation's capture thread pays for reliability with power: `k_busy_wait` spins for essentially the full ~21 ms it takes to fill each 2048-sample block, because a WFI/idle gap between DMA polls lets the 8-word SAI RX FIFO overrun and stall the transfer (their own comment: *"an accepted trade for a working capture"*). Blocks run back-to-back continuously. Running that as-is would keep the MCU near-100% busy for as long as the mic is active — incompatible with the µA-sleep budget the reflex layer is built around.

Separately, the acoustic literature on gunshots matters here: the primary muzzle-blast pulse is short — roughly 2–7 ms outdoors depending on firearm and environment (Maher, "Acoustical Characterization of Gunshots"). That's too short to reliably catch with a coarsely duty-cycled digital sampler without the duty cycle approaching 100%, which defeats the point of duty-cycling for power savings.

Whether the buried SM-24 geophone can stand in as a gunshot trigger (the way it already does for footfall, per ADR 0001) is unconfirmed. Acoustic-to-seismic coupling of airborne gunfire exists in principle, but is weak and short-range, and untested for our soil/geophone/burial-distance combination. No source was found establishing typical detection range for ground-coupled gunfire. Poaching shots we actually care about detecting will often be well outside plausible seismic range while still being acoustically audible much farther out — so treating geophone-wake as sufficient for gunshot specifically (unlike footfall, which ADR 0001 already grounds in published seismology) would be an unverified assumption baked into a safety-relevant trigger.

Worth noting: `bom.md` originally listed the electret + MAX9814 module for exactly this role — *"MCU always-on gunshot (optional)"* — before `procurement-status.md`'s Flag #2 dropped it, on the reasoning that it duplicated INMP441 as a second mic doing the same corroboration job. That reasoning holds for corroboration/classification, but not for a binary always-on wake comparator, which is a different function than the one INMP441 does.

Arduino's own official App Lab `audio_classification` Brick (`arduino/app-bricks-py`) was checked as a possible shortcut for the sustained-event classifier. Its prerequisites are explicit: a USB-C hub and an analog 3.5 mm or USB microphone feeding the QRB2210 side directly, with the Brick listening continuously on the Linux side. That's a materially different architecture from ours — INMP441 is deliberately on the MCU side, event-gated, precisely so the always-on cost lands on the µA-budget reflex layer instead of keeping the MPU continuously awake. The stock Brick's assumption (MPU always listening) isn't available to us without abandoning the whole power argument this ADR makes. Its Python API is still worth reusing where it doesn't conflict: `AudioClassifier.classify_from_file()` takes an offline WAV buffer, which fits the post-wake stage cleanly — a captured MCU window relayed over Bridge/SPI can be written out and classified through the same official call path, so the sustained-event classifier looks idiomatic to anyone familiar with App Lab even though the capture front end is custom.

## Decision

Split the acoustic pipeline into two stages with different trigger models, rather than one "mic corroborates whatever woke the node" design.

**1. Sustained events (chainsaw, vehicle, non-impulsive animal calls) — geophone/periodic-wake-gated, as already scoped.** SAI/INMP441 stays clock-gated during normal sleep. The full capture+FFT routine — reusing Rahul's proven register sequence and pin/clock math, adapted to our own thread-priority scheme with the geophone thread strictly higher priority than any mic thread — only runs for a window after the node is already awake for another reason (geophone trigger, periodic maintenance wake, or the gunshot gate below). These events last seconds, so gating on an already-awake window doesn't risk missing them. Classification (chainsaw vs. vehicle vs. call vs. ambient) runs as a features-plus-classifier pipeline: per-block scalar features (RMS, crest factor, spectral centroid/flatness, zero-crossing rate) over a rolling 1–2 s window, cheap gate on the STM32, richer model on the QRB2210 feeding the log-odds fusion. Rahul's `fuser.cpp` feature set (rms/kurtosis/std/peak/crest_factor/skewness) is a directly reusable template for this, trained against our own labels.

**2. Gunshot wake-gate — dedicated always-on analog front end, separate from INMP441.** Add a cheap electret capsule feeding a comparator (e.g. LM393-class dual comparator; MCP6002 is fully committed to the geophone band-pass and has no spare channel) running continuously at µA-to-low-mA draw, with its output wired to an MCU GPIO/EXTI wake line — the same interrupt-driven wake pattern already used elsewhere in the reflex layer. Its only job is flagging "a loud broadband transient just happened"; it does no classification.

**2a. Cold-start-after-trigger is not acceptable as originally written — this needs a pre-trigger buffer.** The comparator itself responds in microseconds and isn't the bottleneck; the bottleneck is everything downstream of it. If INMP441/SAI is fully clock-gated until the comparator fires and only then begins HSE/PLL2 lock, SAI register setup, and GPDMA channel arm, the wake-to-first-sample latency stacks across several sequential steps — plausibly 1–3ms or more, with no real end-to-end measurement yet. Against a 2–7ms primary muzzle-blast pulse (§Context), a cold-start design risks capturing mostly post-blast decay rather than the diagnostic sharp attack transient, which would materially hurt classification confidence right when it matters most. Capturing only what happens *after* the trigger is the wrong shape for an event this short. Fix, in order of preference:
   1. **True circular/double-buffered DMA on the SAI, kept lightly running rather than fully gated**, so there is no cold start at all — the comparator trigger locks in a rolling window that already contains audio from just before the trigger, the same principle a dashcam's loop-record-plus-pre-roll uses. This promotes the circular-DMA alternative below from "optional v2 experiment" to a load-bearing requirement for this design to be trustworthy, and needs real bench measurement of whether GPDMA1 can free-run without the CPU re-arming it (see Alternatives).
   2. **Keep SAI/PLL2 configured but gated (not torn down)**, so wake is an enable-bit flip rather than a full cold reinit — less latency than option 2 in Context, but not zero, and only worth it if option 1 above proves infeasible on the bench.
   3. **Fall back on the reverberant tail** if neither of the above closes the gap in time — forest gunshot acoustics include a decaying reflected tail past the primary pulse that may still carry a classifiable broadband signature even if the initial attack is missed. This was already flagged as an evidence gap in Consequences; it is now a higher-stakes unknown than originally scoped, since it may end up being the *primary* signal rather than a nice-to-have extension.

Whichever of these three ships, INMP441 stays clock-gated (or lightly circular-buffered per 2a.1) rather than continuously running at full capture+FFT cost — the µA-sleep budget argument from Context still holds. Once real audio is available (pre-trigger buffer or post-trigger window), it powers into a short capture+classify burst (impulsive-shape / crest-factor check on the STM32; escalate to the QRB2210 if ambiguous), same fusion path as stage 1.

This keeps CONTEXT.md's "gunshot trigger" and "geophone STA/LTA" as genuinely separate reflex-layer triggers, not one gating the other — correcting an earlier assumption (raised in this same discussion thread) that the mic could simply ride on the geophone's wake-up for every event type. That assumption is fine for elephant presence/movement; it doesn't hold for gunshot given the coupling-range uncertainty above.

## Alternatives considered

- **Continuous circular/double-buffered DMA capture on INMP441, with only a cheap RMS/peak check (no FFT) as the always-on gate, no new hardware.** Rahul's busy-poll requirement comes from a single-block re-arm-per-FFT-window DMA design, not necessarily a hardware limit — a true circular buffer might let GPDMA1 free-run without CPU re-arming and tolerate WFI between light checks. Originally filed here as an optional "not now" item; superseded by §2a above, which makes this load-bearing rather than optional — a cold-start wake-gate risks missing the 2–7ms blast pulse entirely (see §2a), so this needs to be bench-tested before the wake-gate design can be trusted, not deferred past the freeze.
- **Duty-cycled INMP441 sampling (brief periodic SAI wake, check amplitude, sleep), no new hardware.** Rejected: the 2–7 ms primary blast pulse is short enough that bounding miss probability needs a duty cycle near 100%, which isn't really duty-cycling anymore — and every SAI burst still pays a busy-poll cost per Rahul's findings.
- **Rely on the geophone as the sole gunshot trigger.** Rejected: no evidence the buried 10 Hz geophone reliably picks up airborne gunfire at the standoff ranges anti-poaching detection actually needs; footfall/movement coupling is well-established (ADR 0001), gunshot coupling is not.
- **Leave MAX9814/electret dropped, treat gunshot detection as best-effort.** Not recommended — CONTEXT.md names gunshot detection as an explicit reflex-layer duty and a DFO-relevant anti-poaching feature — but this is the fallback if the hardware reconsideration below is rejected.

## Consequences

- One new cheap component class if accepted: electret capsule + LM393-class comparator. Negligible cost and lead time next to the real bottleneck in `procurement-status.md` §6 (power system) — this would not be on the Aug 8 critical path. Hand-built on perfboard/dotted-PCB, consistent with the rest of the analog front-end — no fab turnaround risk.
- INMP441's full SAI/PLL2/GPDMA/CPU chain only ever runs event-triggered under this design, never continuously, protecting the always-on power budget regardless of which sustained-event trigger fires it.
- **Reopens a procurement line explicitly marked "dropped"** (`procurement-status.md` Flag #2). The role proposed here (binary wake comparator, zero classification capability) is different from the role that drop reasoning was rejecting (a second classification mic redundant with INMP441) — bom.md's original "MCU always-on gunshot" note for this exact part supports that reading — but this still needs explicit sign-off before this ADR moves to accepted or `bom.md`/`procurement-status.md` get touched.
- Open items requiring bench validation before "accepted", in priority order:
  1. **Measure real end-to-end wake-to-first-sample latency** (comparator trigger → HSE ready → PLL2 lock → SAI/GPDMA armed → first sample in buffer) on actual hardware. This number determines whether §2a's cold-start risk is real or negligible, and gates every other decision about the pre-trigger buffer.
  2. Whether a true circular/double-buffered GPDMA1 capture (§2a.1 / Alternatives) is achievable without the CPU re-arming it per block, and whether it can tolerate WFI between light amplitude checks — the preferred fix if latency in (1) turns out to matter.
  3. Whether local forest reverberant tail meaningfully extends the detectable window past the bare 2–7 ms primary pulse — now the fallback if (2) isn't achievable in time, not just a nice-to-have; no figure found in the literature search for this project.
  4. Comparator threshold/hysteresis tuning against real gunshot recordings and local ambient noise (wind gusts, thunder, branch-fall are also broadband transients and will false-trigger a naive threshold).
  5. Confirming geophone gunshot coupling is genuinely not viable at operational range, rather than assumed — no direct source found either way; flagged as an evidence gap, not a settled negative.
  6. Thread-priority rework needed regardless of which gate design ships: geophone strictly above any mic thread in the reflex-layer scheduler, mirroring the reasoning (not the exact priority numbers) in the reference implementation's `app_config.h`.
