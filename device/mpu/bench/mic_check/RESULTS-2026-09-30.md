# Microphone bench run — 30 September 2026

First run of the acoustic capture path on real hardware. Recorded because three
things came out of it that are not re-derivable from the code: a capture defect
that is now fixed, a sample-rate question that is now closed, and the first
end-to-end inference through the production client.

## Rig

| | |
|---|---|
| Board | UNO Q, `arduino@192.168.1.4`, App Lab 0.11.0 |
| Capture device | Microdia `0c45:6366` USB webcam mic, ALSA card 1, `plughw:1,0` |
| Model | `etx-acoustic-panns-20260930`, EI project **1110036 "ETX-Test"**, impulse 19 |
| Runner | `edge-impulse-linux-runner --model-file <eim> --run-http-server 1400`, host-side under Node |
| Room | Quiet indoor, no deliberate stimulus |

**This is not the mic that will be fielded.** The BOYA BY-M1 is not procured and
uses a different USB adapter. Everything below is the right order of magnitude
for the acoustic path, and none of it is a calibration for the fielded chain.

The registered model is the production one. 1110036 is named `ETX-Test` because it
began as the scratch project, but it now carries the shipping PANNs impulse — see
[ADR 0032](../../../../docs/decisions/0032-acoustic-production-project-is-1110036.md).
Nothing below is an accuracy measurement in any case; these are latency and
capture-quality numbers, taken in a quiet room with no labelled stimulus.

## 1. Capture warm-up transient — a real defect, now fixed

Every fresh `arecord` open produces a large decaying transient. Because
`Microphone.capture()` deliberately spawns a new `arecord` per call, it is paid
on **every** capture, not once at startup.

| window | rms | peak | clipped | dc |
|---|---|---|---|---|
| 0–1 s | 0.16662 | 1.0000 | 1.25e-4 | −0.11704 |
| 0–4 s | 0.09080 | 1.0000 | 3.10e-5 | −0.00326 |
| 4–12 s | 0.00795 | 0.0302 | 0 | +0.00118 |
| 8–12 s | 0.00727 | 0.0264 | 0 | +0.00020 |

Reproducible to three significant figures across separate captures, which is
what distinguishes it from a real scene.

The first second hard-clips at full scale and carries a DC offset of −0.117 —
on its own 2.3× `ACOUSTIC_MAX_DC_OFFSET`. Averaged over a whole clip it
disappears, so the health gate passed a clip whose loudest content was pure
artifact and handed it to the classifier as signal.

Fixed by `Microphone.WARMUP_S = 4.0`: the warm-up is recorded inside the same
`arecord` run (a separate throwaway capture would not help — the transient
belongs to opening the PCM, so a second open reproduces it) and discarded
*before* levels are measured, so the health gate describes the settled stream
only. Effect on the same rig:

| | before | after |
|---|---|---|
| peak | 1.0000 | 0.0277 |
| clipped samples | 1–3 | 0 |
| dc | 0.0177 | 0.00091 |

The true noise floor (~0.006) is only visible once the discard is in place.

## 2. Sample rate — the hardware takes 8 kHz natively

```
$ arecord -D hw:1,0 -f S16_LE -c 1 -r 8000 -d 1 --dump-hw-params /dev/null
RATE: [8000 48000]

$ arecord -D hw:1,0 -f S16_LE -c 1 -r 8000 -d 1 -v /dev/null
  rate         : 8000
  exact rate   : 8000 (8000/1)
```

So **no ALSA software resampling happens on the capture path** and `plughw:`
passes 8 kHz through untouched. The comment in `services/config.py` that said
`plughw:` was converting in-kernel from a 44.1/48 kHz-only codec was inaccurate
for this device and has been corrected.

Consequence: there is no decimation leg here to write a parity test against.
The only resampling on the path is the 8k→32k upsample inside the PANNs DSP
block, which `dsp-panns-logmel/cpp/parity_resample.py` already covers.

Re-measure against the BY-M1's adapter before assuming this carries over. If
that adapter advertises 44.1/48 kHz only, `plughw:` *will* decimate and the leg
becomes real and untested.

## 3. First end-to-end run through the production client

Through `HttpAcousticClassifier`, against a runner started exactly the way the
vision one is:

```
model      labels=['ambient', 'chainsaw', 'elephant_call', 'gunshot']
           freq=8000.0Hz window=10.00s features=80000
capture    15.00s needed for 2 windows
           15.00s from plughw:1,0 in 19.2s wall (+4s warm-up)
           rms=0.014055 peak=0.0555 clipped=0.000000 dc=+0.000589
health     PASS
inference  8.7s for 2 window(s) (4.4s each)
  win0    ambient        0.8933   ambient=0.893 chainsaw=0.028 elephant_call=0.043 gunshot=0.036
  win1    ambient        0.9525   ambient=0.953 chainsaw=0.013 elephant_call=0.021 gunshot=0.013

selected   ambient @ 0.9525
```

Four repeats of the capture stage gave rms 0.0057–0.0141, peak 0.023–0.056,
clipped 0.000000 throughout, dc +0.00059–+0.00078.

**Latency: 4.0–4.4 s per window**, which matches Studio's 4,134 ms estimate for
the classifier block. That also settles a figure `config.py` recorded as
unknown — Studio cannot profile a custom DSP block, so the log-mel block's cost
was unestimated; the measured total being within ~7% of the classifier-only
estimate means the custom block is small, not hidden.

`ACOUSTIC_INFERENCE_TIMEOUT_S = 15.0` is therefore ~3.5× the measured per-window
cost. Adequate, and worth keeping as a wedged-runner ceiling rather than
tightening toward the measurement.

## Facts worth not re-deriving

- The impulse is **8000 Hz / 80000 features** (10 s window), 4 labels, deploy
  version 7. Confirmed from the binary via `model.eim --print-info`.
- Features are the **raw int16 PCM values sent as-is, not normalised to ±1** —
  this is a non-camera impulse. `POST /api/features` 400s on any count that is
  not exactly `input_features_count`.
- The raw `.eim` alone will not serve HTTP. `--run-http-server` is a flag of the
  Node CLI wrapper; the bare binary takes `--print-info`, `stdin`, or a socket
  name, needs a `{"id":N,"hello":1}` handshake, and passes features through
  POSIX shared memory (`features_shm`), not inline JSON. Use the Node CLI.
- The board's deployed `python/` tree predates the acoustic work —
  `perception/microphone.py` is not on the board at all. All of the above was
  staged outside the bind mount and removed afterwards; the running app was
  never touched.
